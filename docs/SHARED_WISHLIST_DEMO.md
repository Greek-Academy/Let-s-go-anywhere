# 「行きたい」を持ち寄る共有リスト — 今回の確認方法

Issue #90 / 親Issue #40。今回は、TimeTreeのように「新しいリストを作り、相手を招待する」操作を、1台の端末で確かめる実装です。**別のiPhoneとの共有は、まだ動きません。** Firebaseプロジェクトは未作成と確認しています。

## まず3つ試してください

1. **リストを作る**：「行きたい」→「私の行きたい」の切り替えボタン→「新しいリストを作る」。名前と色を選びます。
2. **相手を招待する**：右上の歯車→「デモの招待を作る」→「招待される側を試す」→参加申請→「作成者として承認を試す」→承認。申請しただけでは相手役に候補は表示されません。
3. **候補を持ち寄る**：リストの「候補を追加」→自分の保存か公開ページURLを選ぶ→共有前に内容を確認。画面の「あなた」「はる（デモ）」を切り替え、それぞれ反応します。両者が「行きたい／気になる」なら「二人とも興味あり」で表示されます。

候補を先に追加してから招待することもできます。「見つける」の既存お出かけ詳細・Web候補詳細からも「共有リストに追加」で進めます。戻る操作は直前の画面へ戻ります。絞り込みはURLに残るため、候補詳細から戻ったときも引き継がれます。

デモ用の「はる」は架空の相手です。他の人がログインしたわけではありません。操作役の切り替えは、共有画面の挙動を試すためにだけ使います。この端末の個人保存の持ち寄りは「あなた」の役だけに表示し、はる役にはリンク入力を用意しています。下部の「行きたい」タブは従来の個人保存へ戻ります。再読み込み時の操作役は「あなた」です。

## 今できること

- リスト作成・切り替え・名前と色の変更。1役あたり3リスト、1リスト100候補。
- 個人保存から選んだ1件、Web候補、持ち込みURLを共有前に確認。自動取得や外部送信はありません。
- 招待発行・参加申請・作成者の承認／却下・申請辞退。7日間・1人分・取り消し・再発行。承認時にも期限を確認します。
- 「行きたい」「気になる」「今回は見送り」「未回答」。自分の反応だけを変更。
- 自分の追加した候補の共有メモ編集、候補の削除、URLまたは同じ掲載IDによる重複防止。
- 共有候補の詳細・出典・未確認／サンプル表示。「私の行きたいにも保存」は、現在の掲載候補か実リンクで利用できます。
- メンバー退出・作成者による削除・作成者の引き継ぎ依頼と承諾・リスト全削除。
- この端末での保存と再読み込み。保存失敗時は入力と最後に保存したデータを残します。

退出者が追加した候補・明示した共有メモは残ります。追加者を匿名化し、退出者の反応と関連する申請情報を消します。作成者は、残ったメンバーが引き継ぎを承諾してから退出できます。1人ならリスト全削除を使えます。

デモ招待リンクは `driveplus-demo://invite/…` です。**LINE等で送っても別端末からは参加できません。** 外部への共有メニュー・送信完了表示は追加していません。「デモ招待リンクから参加」は、同じ端末にある招待の確認用です。

## 個人データ・費用への影響

個人の保存、学習履歴、チェック回答、不安、位置情報、プロフィール、個人メモは自動で共有候補に入りません。選んだ名称・地域・URL・状態・日時と、自分で書いた共有メモだけを取り出します。候補のタイトルやURL自体に私的な情報が含まれる場合は、共有前に確認してください。

元の個人保存と共有候補は別のコピーです。片方を削除しても、もう片方は消えません。写真は共有データにアップロードせず、このアプリにある利用条件を確認できたサンプル画像のみ表示します。Web候補や持ち込みURLの写真は取得しません。

追加料金0円。新しいSDK、クラウドサービス、SNS API、OpenAI API呼び出しはありません。既存の実検索3回の枠は消費しません。出典を開く操作を選んだときだけ、従来の確認モーダルを経て外部ページへ進みます。

## 実際の別端末共有に残っていること

[Firebase準備の手順](SHARED_WISHLIST_FIREBASE_SETUP.md)を参照してください。

- ログイン・本人確認、Firebase Authentication接続。
- Firestoreへの保存と取得、参加者だけに読み書きを許すサーバー側のルール、Emulatorテスト。
- 実招待用HTTPSページ、2人・別アカウント・別端末での往復確認。
- バックグラウンド・ログアウト・権限失効時の表示破棄、削除途中の再開、アカウント削除。
- 本人ごとの反応を別文書で保存する同時更新対策、サーバー時刻での期限判定。
- 任意の表示名、5人参加時の実機確認、前回開いたリストのタブ間復元、写真利用停止を複数端末へ伝える運用。
- 候補の名称・URL編集（今回編集できるのは共有メモ）、Webサンプルを含む全候補形式の個人側への逆保存。

デモの操作役の切り替えや端末内の権限チェックは、本物の認証・アクセス制限にはなりません。親Issue #40は未完了として残します。

## 実装の分け方（開発向け）

| 場所 | 役割 |
| --- | --- |
| `src/sharing/model.ts` | 個人データを含まない共有候補、リスト、招待、反応の型 |
| `src/sharing/candidates.ts` | 個人保存から許可した項目だけ取り出す変換 |
| `src/sharing/domain.ts` | 招待・承認・反応・退出などのデモ内ルール |
| `src/sharing/codec.ts` | 保存形式の検証。未対応・不正なデータを保護 |
| `src/sharing/repository.ts` | 保存の窓口と端末内デモ実装。保存成功後にだけ画面へ反映 |
| `src/sharing/SharingProvider.tsx` | 読み込み・操作役・処理中／エラーの管理 |
| `src/sharing/components.tsx` / `sharing.css` | 共有前の確認・候補カード・共通表示 |
| `src/screens/SharedLists.tsx` | 一覧、作成、詳細、招待、メンバー・設定 |

WebはlocalStorage、iPhoneはPreferencesの **`driveplus.sharing.demo.v1`** に保存します。既存の`driveplus.mock.v1`は移行・書き換えません。掲載情報確認ツールでは専用メモリを使い、端末内の共有保存を読み書きしません。設定の「モックの保存データを削除」は両方を削除します。共有側の削除に失敗した場合は個人側の削除へ進みません。別キー間の削除はトランザクションではなく、後半の個人側だけ失敗した場合は個人データの再削除が必要です。

デモの保存は直列化し、Web Locks対応ブラウザでは同じキーへの書き込みを排他します。読み込んだ元文字列と現在の保存を比較し、古い画面からの上書きを停止します。Web Locks非対応環境の複数タブ同時編集は保証しません。iPhoneのデモは単一アプリ実行を対象とします。

Firebase実装は、この画面の保存窓口を活用しつつ、認証済みユーザーID・必要なリストだけの取得・文書単位のルール／トランザクションへ分けます。端末全体のデモJSONをそのままクラウドへ送る置き換えにはしません。
